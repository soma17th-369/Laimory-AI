# 실행계획 템플릿

아래 골격을 복사해 실제 내용으로 채운다. 빈 설명용 주석은 제거한다.

**순서를 지킨다.** 첫 요약만 읽어도 이슈를 연 이유인 현재 문제와 해결 방향, 완료 후
달라지는 결과를 알 수 있어야 한다. 상세 근거와 긴 배경만 그 뒤에 둔다.

```markdown
---
title: 작업 제목
status: draft
created_at: YYYY-MM-DDTHH:MM:SS+09:00
updated_at: YYYY-MM-DDTHH:MM:SS+09:00
approved_at:
approved_by:
completed_at:
issue:
branch:
---

# 작업 제목

## 요약

- 문제: 현재 어떤 동작이나 제약 때문에 무엇이 어려운지 적는다.

- 해결: 이번 작업에서 어떤 방식으로 문제를 해결할지 적는다.

- 결과: 완료 후 사용자나 시스템 관점에서 무엇이 달라지는지 적는다.

## 실행 단계

### 1. 구체적인 변경 단계

변경할 대상과 완료 후 달라지는 동작을 1~2문장으로 적는다.

### 2. 구체적인 변경 단계

변경할 대상과 완료 후 달라지는 동작을 1~2문장으로 적는다.

### 3. 테스트와 검증

실행할 검사와 통과 기준을 1~2문장으로 적는다.

## 승인 전 결정

사용자가 골라야 하는 것만 적는다. 각 항목은 «선택지 + 권장안 + 한 줄 이유»로 쓴다.
내가 판단해도 되는 것은 여기 올리지 않고 실행 단계에 녹인다. 없으면 `없음`이라고 적는다.

## 검증

- 실행할 명령

- 완료를 판단할 기준

---

## 범위

- 포함할 변경

## 제외 범위

- 이번 작업에서 하지 않을 것

## 현재 구조

- 확인한 관련 파일과 현재 동작 (`경로:줄번호`로 가리킨다)

- 보존해야 할 계약과 기존 사용자 변경

## 위험과 롤백

- 실패 가능성과 대응 방법

## 승인 기록

- 승인 상태: 대기

- 승인 내용:
```

계획 전체 상태는 `draft → approved → in_progress → completed` 순서로 바꾼다. 한 번의 승인이 모든 실행 단계에 적용되므로 단계별 상태나 개별 승인 항목은 만들지 않는다. 중단 시에는 계획 전체 상태에 `blocked` 또는 `cancelled`를 사용한다. 승인 뒤 계획이 실질적으로 변경되면 `draft`로 되돌리고 재승인받는다.

## 분량 기준

- `요약`, `실행 단계`, `승인 전 결정`, `검증`까지가 승인에 필요한 전부다. 화면 하나에 들어가게 쓴다.
- 요약의 문제·해결·결과는 각각 1~2문장으로 쓴다. 문제를 이해하는 데 필요한 직접적인 배경은
  포함하되, 긴 연혁·세부 파일 구조·조사 근거는 `현재 구조`로 내린다.
- 실행 단계는 번호가 붙은 소제목으로 분리하고 수행 내용만 적는다. 상태 행, 개별 승인 항목, 체크박스는 넣지 않는다.
- 단계, 결정, 검증 등 서로 다른 문항과 목록 항목 사이에는 빈 줄을 하나 둔다.
- `현재 구조`는 길어도 된다. 대신 `---` 아래에만 둔다.
- 같은 내용을 위아래에 두 번 쓰지 않는다. 결정의 근거는 `승인 전 결정`에 한 줄, 자세한 사실은 `현재 구조`에 둔다.
