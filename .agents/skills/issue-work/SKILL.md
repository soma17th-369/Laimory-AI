# issue-work

GitHub 이슈를 받아 **실행계획을 세우고**, 사용자와 **대화하며 작업을 진행**한다.
이슈 내용 조회만 스크립트가 맡고, 계획 수립과 실제 작업은 이 문서를 따르는 Claude가 한다.

## 핵심 규칙

- 작업할 이슈 번호는 다음 우선순위로 정한다.
  1. 명령과 함께 이슈 번호가 주어지면(예: "이슈 23 작업해줘", "$issue-work 23") 그 번호를 쓴다.
  2. 번호가 없으면 현재 브랜치명에서 `#<번호>`를 추출해 그 이슈로 작업한다.
  3. 둘 다 없으면 중단하고 이슈 번호를 알려달라고 요청한다.
- 이슈 내용을 충분히 읽고 이해한 뒤에 실행계획을 세운다. 추측으로 진행하지 않는다.
- 실행계획은 반드시 **사용자에게 먼저 보여주고 확인받은 뒤** 작업을 시작한다.
- 작업은 한 번에 다 하지 않고, 계획의 단계 단위로 사용자와 대화하며 진행한다.
- 이 스킬은 코드 작업까지만 한다. 커밋·push·PR 생성은 하지 않는다. 그 단계는 `$issue-pr`로 넘긴다.
- 사용자가 명시하지 않은 파일 삭제, `git reset`, `git checkout` 같은 파괴적 작업은 하지 않는다.
- 기존 변경사항이 있으면 사용자 작업으로 보고 되돌리지 않는다.
- 사용자에게 보이는 계획, 진행 보고는 한글로 작성한다.
- 토큰은 절대 출력, 보고에 포함하지 않는다.

## GitHub 토큰 준비

- `GITHUB_TOKEN` 환경 변수가 가장 우선이고, 없으면 저장소 루트의 `.env.local`에서 읽는다.
- `.env.local`에는 `GITHUB_TOKEN=ghp_xxx` 한 줄로 저장하고 커밋하지 않는다.
- 토큰이 없으면 스크립트가 중단하고 설정 방법을 안내한다. 토큰 값은 어떤 출력에도 노출하지 않는다.

## 작업 절차

### 1단계 — 이슈 내용 가져오기

명령에 이슈 번호가 있으면 `--issue`로 넘기고, 없으면 생략해 브랜치명에서 추출하게 한다.

```powershell
# 이슈 번호를 명시한 경우
python .agents/skills/issue-work/scripts/issue_work.py fetch --issue 23

# 번호 없이 현재 브랜치명의 #번호 사용
python .agents/skills/issue-work/scripts/issue_work.py fetch
```

출력 JSON에서 `issue`, `title`, `state`, `type`, `labels`, `body`, `sub_issues`를 확인한다.
이슈 번호를 찾지 못하거나 토큰이 없으면 중단하고 필요한 조치를 보고한다.

### 2단계 — 이슈 이해 & 컨텍스트 파악

- 이슈 본문(`body`)을 끝까지 읽고 요구사항, 완료 조건, 체크리스트를 파악한다.
- `type`(Bug/Feature/Task 등)에 따라 작업 성격을 맞춘다.
  - **Bug**: 영향받는 동작, 재현 경로, 에러/로그, 수정 지점을 찾는다.
  - **Feature**: 구현할 기능, 변경 파일, DB/API 영향, 체크리스트를 정리한다.
  - **Task(리팩터링 등)**: 대상 범위, 사유, 보존해야 할 동작을 확인한다.
- `sub_issues`가 있으면 어떤 하위 작업이 이번 범위인지 사용자와 정한다.
- 이슈가 가리키는 실제 코드를 읽어 현재 구조를 확인한 뒤 계획을 세운다.

### 3단계 — 실행계획 수립 & 확인

이슈와 코드 파악을 바탕으로 단계별 실행계획을 한글로 만들어 사용자에게 보여준다. 예:

```
이슈 #23 "로그인 토큰 만료 처리" 실행계획:
1. app/auth/token.py 의 만료 검증 로직 확인
2. 만료 시 401 + 재발급 안내 응답 추가
3. 관련 테스트(tests/test_auth.py) 보강
4. 동작 확인

이대로 진행할까요? 수정할 부분이 있으면 알려주세요.
```

- 범위·우선순위·접근 방식 중 애매한 부분이 있으면 `AskUserQuestion`으로 확인한다.
- 계획이 길거나 단계가 많으면 `TaskCreate`로 작업 목록을 만들어 진행 상황을 추적한다.
- **사용자 확인 전에는 코드를 수정하지 않는다.**

### 4단계 — 단계별 작업 진행

확인된 계획에 따라 한 단계씩 진행한다.

- 각 단계를 시작할 때 무엇을 할지 짧게 알리고, 끝나면 결과를 보고한다.
- `TaskUpdate`로 단계 상태를 `in_progress` → `completed`로 갱신한다.
- 변경 범위에 맞는 focused test나 검증을 단계마다 실행한다.
- 계획에서 벗어나야 할 상황이 생기면 멈추고 사용자와 다시 상의한다.
- 사용자가 다음 단계로 넘어가라고 하기 전에 다음 단계를 미리 진행하지 않는다.

### 5단계 — 마무리 안내

이슈 범위의 작업이 끝나면 다음을 보고한다.

- 처리한 이슈 번호와 제목
- 단계별로 무엇을 했는지 요약
- 변경한 파일과 실행한 검증 결과
- 커밋/PR이 필요하면 `$issue-pr` 스킬로 진행하면 된다고 안내한다(이 스킬은 커밋·PR을 하지 않는다).

## 참고 자료와 스크립트

- 이슈 조회 헬퍼: [scripts/issue_work.py](scripts/issue_work.py)

스크립트는 다음을 보장한다.

- 명령 인자(`--issue`) 또는 현재 브랜치명에서 이슈 번호 결정
- 원격 저장소 owner/repo 확인
- `GITHUB_TOKEN` 환경 변수 또는 `.env.local` 토큰 사용
- GitHub 이슈 본문, 상태, 타입, labels, assignees, 하위 이슈 조회
- GitHub API 응답을 UTF-8로 처리해 한글 깨짐 방지
